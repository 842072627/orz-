我为你设计了一套 “腹地-主干道分层潮汐调度”（Hinterland-Trunk Tidal Layering） 方案。这不再是现有逻辑的修补，而是一种全新的架构，旨在从根本上解决饥饿与拥堵的矛盾。核心理念是：将主走廊从“被动瓶颈”转变为“主动管理的高吞吐量干线”，并与腹地区域的执行策略解耦。

核心洞察与解决方案设计
问题的根源在于，每个智能体都试图在不确定全局走廊容量的情况下独立规划穿越主走廊的路径，调度器只能被动地批准或拒绝整个穿越请求。

我的方案核心思想是反转控制权：像管理一条受严格管控的单向铁路或高速公路一样管理主走廊。任务分配必须提前预定“路权”。

方案由三个核心机制构成：

1. 潮汐腹地任务池 (Tidal Hinterland Task Pool)

逻辑分区：用中心线 main_dist 将地图动态划分为左腹地和右腹地。

方向配额：如果主走廊潮汐方向是左→右，当前调度周期就仅从右腹地的任务池中分配任务。方向为右→左时，则只分配左腹地的任务。

效果：这保证了分配的每一对任务（智能体与终点）都能自然地顺应潮汐方向，路径不冲突，从根本上消除了被方向锁阻挡的可能性。

2. 干线通行证预约 (Trunk Transit Token Reservation)

容量管理：像活动计数器一样追踪主走廊，但不是在物理实体进入时增加，而是在分配任务时根据其预定的穿越路径，在预期的未来时间片上预约“容量”。

分配决策：在 base_score 中增加一个核心检查：仅当任务所需穿越的所有主走廊段，在其预期的穿越时间均有可用容量时，才允许分配该任务。

效果：这实现了可预测的、零冲突的干线交通流。它将走廊从共享的、易发拥堵的空间，转变为一个无冲突的、铁路式的调度系统。一旦预约成功，执行过程就不会遇到意料之外的硬阻塞。

3. 可抢占式腹地执行 (Preemptible Hinterland Execution)

混合策略：在腹地区域，放开对任务的限制，使用软惩罚评分系统，鼓励智能体在主干道之外积极执行任务。

状态监控：为智能体设置任务“截止时间”。如果一个智能体的主走廊通行证即将生效，但它因腹地任务而无法准时到达入口，就强制抢占其当前腹地任务，让它空载前往汇合点，以配合宏观主干道节奏。

效果：这保证了即使在等待通行证期间，智能体的利用率也近乎 100%，但绝不会因贪恋小任务而错过干线班次，避免了整个系统的脱节。

可行性论证
这个方案直接从问题的根源入手：

解决饥饿：通过严格的容量预约，它为安全分配创造了可能性。这与原来因为盲目封锁而没有任何任务能通过瓶颈的情况有本质区别。

解决拥堵崩溃：通过执行严格的基于预约的准入控制，它变得可预测。它能保证干线上不会发生拥堵，并从系统中彻底消除了“拥堵崩溃”这种失效模式。

解决方向锁死：潮汐腹地任务分配消除了冲突。它不再是被动应对错误路径的请求，而是直接创建出方向永远正确的任务。

// src/centerline.h

namespace Centerline {

// ... 保留所有现有代码（状态变量、update_zone24_density等）...

// ========== 新的全局潮汐状态 ==========
static int g_tidal_direction = +1; // +1: 左->右, -1: 右->左
static int g_tidal_period = 500;   // 潮汐切换周期（可根据任务完成率动态调整）
static int g_tidal_step_counter = 0;

// ========== 干线容量预约系统 ==========
struct TrunkToken {
    int start_step;  // 通行证生效时间
    int end_step;    // 通行证失效时间
};

// 每个主走廊段是一个map: segment_main_dist -> 容量时间表
// 用vector<int>模拟未来时间片的容量，简化示例用
static std::unordered_map<int, std::vector<int>> g_trunk_schedule; 
static constexpr int TRUNK_CAPACITY_PER_STEP = 5; // 每时间步每段允许预约5个智能体

// 初始化及重置通行证调度表（在init或每个调度周期开始时调用）
void reset_trunk_schedule(int total_len, int horizon) {
    g_trunk_schedule.clear();
    // 按需惰性创建
}

// 检查并预约从a_m移动到b_m（穿越主走廊段）的容量
bool try_reserve_token(int a_m, int b_m, int current_step, int travel_time) {
    // 确定穿越的主走廊段（简化：方向上的所有main_dist整数区间）
    int lo = std::min(a_m, b_m);
    int hi = std::max(a_m, b_m);
    int start = current_step; // 当前步预约
    int end = current_step + travel_time + 10; // 预留缓冲

    for (int m = lo; m <= hi; ++m) {
        auto& schedule = g_trunk_schedule[m]; // 惰性resize
        for (int t = start; t <= end; ++t) {
            if (t >= (int)schedule.size()) schedule.resize(t + 1, 0);
            if (schedule[t] >= TRUNK_CAPACITY_PER_STEP) {
                return false; // 容量不足，预约失败
            }
        }
    }
    // 预约成功
    for (int m = lo; m <= hi; ++m) {
        auto& schedule = g_trunk_schedule[m];
        for (int t = start; t <= end; ++t) {
            if (t >= (int)schedule.size()) schedule.resize(t + 1, 0);
            schedule[t]++;
        }
    }
    return true;
}

// 更新潮汐方向 (在pre_tick_updates中调用)
void update_tidal_direction() {
    g_tidal_step_counter++;
    if (g_tidal_step_counter > g_tidal_period) {
        g_tidal_direction *= -1;
        g_tidal_step_counter = 0;
        // 清除旧的预约表，切换方向后重新构建
        g_trunk_schedule.clear(); 
    }
}

// 检查task_locs的腹地归属是否为当前潮汐方向的有效目标
bool is_task_in_valid_hinterland(int agent_main_dist, const std::vector<int>& task_locs) {
    if (!g_ready) return true; // 未初始化，放行
    // 简化：检查首个errand位置
    if (task_locs.empty()) return false;
    int t_m, t_b;
    project(task_locs[0], t_m, t_b);
    if (t_m < 0) return true; // 不在主走廊上的任务，暂时放行
    
    int intent = (t_m > agent_main_dist) ? +1 : -1;
    return intent == g_tidal_direction; // 任务方向必须与潮汐方向一致
}
