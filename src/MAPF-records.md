### 禁止重复测试

> **重复测试 = 浪费生命。只有以下情况才重复测试：**
>
> 1. **信号不明确**：提升/下降在 5% 以内，需要确认
> 2. **调试需要**：验证编译是否正确（看编译输出，不跑完整测试）
> 3. **用户要求**：用户明确要求重新测试

> **不需要重复测试的情况：**
> - 验证回退成功（看编译，不跑测试）
> - 同一个实验方向已经跑过 3+ 次
> - 信号已经明确（提升 >15% 或下降 >10%）

## 架构差异分析

### Team_Kitty_Knight (9.039)
```
causal_pibt->multi_step() → LNS全局优化 → actions
```

### 我们当前架构 (H1 baseline)
```
plan() → 单次FW优化 → actions
```

**核心差距**：LNS 在每步做全局优化，我们只在 step 0 做一次

**现有类似功能**：
- `get_gp_h()` 使用 `traj_dists` 进行启发式
- `flow.cpp` 初始化 `traj_dists`
- `frank_wolfe()` 优化流量分配

**完整 LNS 需要**：multi_step() + solve() + GlobalManager（较大架构改动）

## 架构调整实验记录

### Round 404: 架构调整1 - 每步运行LNS (失败)
- **假设**: 像 Team_Kitty_Knight 那样每10步运行一次LNS可以提升性能
- **改动**: 在 step loop 中每10步运行 LNS (1 iter, 15ms)
- **结果**: 失败 ❌
  - fulfill: 0.788 vs H3-v4 0.805 (-2%)
  - room: 0.180 vs H3-v4 0.193 (-7%)
  - iron: 0.146 vs H3-v4 0.150 (-3%)
- **原因**: 重新优化破坏已有路径；我们的LNS没有碰撞检测
- **结论**: H3-v4 架构（LNS只在初始化时运行一次）是最优的

### Round 405: 回退确认
- **目的**: 确认回退到 H3-v4 成功
- **结果**: 正常
  - random: 0.500, bos: 0.237, room: 0.180, maze: 0.096
  - fulfill: 0.760, orz: 0.215, iron: 0.141
- **结论**: H3-v4 代码正常
