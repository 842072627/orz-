## 问题分析

### DefaultPlanner flow.cpp 的问题 (关键发现！)

DefaultPlanner 的 frank_wolfe 是**循环遍历所有 agent**，每个 agent 都用 `timelimit`（无限时间）：

```cpp
// DefaultPlanner flow.cpp (line 115-127)
int count=0;
int a, index;
while (std::chrono::steady_clock::now() < timelimit){
    index = count % lns.env->num_of_agents;  // 循环遍历所有 agent
    a = replan_order[index].id;
    count++;
    // ...
    if (!update_traj(lns,a, &timelimit)){  // 每个 agent 用 full timelimit!
        // ...
        break;  // 一个失败就退出
    }
}
```

**问题**：
1. 循环遍历所有 agent，不是像 Team_RAPID 那样只处理 neighbor_size=8 个
2. 没有 deadline_per_agent 的概念
3. 一个 agent 失败就 break

### MyPlanner my_flow.cpp 的改进 (A118)

MyPlanner 有 neighbor_size 批处理的概念：

```cpp
// MyPlanner my_flow.cpp (line 148-186)
int processed_count = 0;
while (std::chrono::steady_clock::now() < timelimit && processed_count < agent_count) {
    int deadline_per_agent = std::max(10, (int)(remaining_ms / neighbor_size));
    
    // Process up to neighbor_size agents starting from processed_count
    int start_idx = processed_count;
    int end_idx = std::min(start_idx + neighbor_size, agent_count);
    // ...
}
```

这更接近 Team_RAPID 的方法，但 room 用 MyPlanner 却更差。

## 下一步方向

### A129: 测试 neighbor_size=4 for room

假设：room 150 agents，如果 neighbor_size 太小，每个 agent 获得的时间太多可能导致效率问题。

等等，这个假设是错误的。neighbor_size 小意味着每批处理更少 agent，每个 agent 的 deadline 更长。

neighbor_size=8 时: deadline = remaining_ms / 8
neighbor_size=4 时: deadline = remaining_ms / 4 (更长)

所以 neighbor_size=4 会给每个 agent 更多时间，可能会更好。

### 另一个方向: 研究 room 是否需要不同的策略

room 地图特征：
- 64x64 开放地图
- 11% 障碍物
- 2.6% 狭窄度
- 150 agents

这和 random (64x64, 10% 障碍物, 6.5% 狭窄度, 400 agents) 有些相似。

## 结论

room 的问题可能是：
1. DefaultPlanner 没有 neighbor_size 概念
2. MyPlanner 的 neighbor_size=8 对 room 不够优化

需要测试 neighbor_size=4 对 room 的影响。
