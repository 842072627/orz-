## 🚀 快速开始

### 第一次使用 Workflow

1. **阅读本文档**：通读一遍，了解完整流程
2. **检查清单**：确认必读清单全部完成
3. **建立基准**：运行 Start-Kit 获取基准分数
4. **开新 ARCH**：从 Start-Kit 纯净基准开始

### 永远活跃流程

```
每次触发（Heartbeat）时：

1. 读取 HEARTBEAT.md 和 src/MAPF-records.md
2. 查阅今天的新资料、新灵感
3. 反思历史：上次为什么失败/成功？
4. 研究当前最优方向：查资料、浏览网页
5. 明确今天最重要的任务
6. 执行最重要的任务
7. 沉淀今天的收获到文档
```

### 每日研究循环（核心任务）

```
每天开始前：
1. 读取 src/MAPF-records.md（知识库、假设追踪）
2. 读取 项目笔记.md（今天的灵感）
3. 查阅新资料（冠军代码/论文/网页）
4. 反思历史（为什么失败/成功？）
5. 明确今天最重要的 1-2 个任务
6. 执行任务
7. 沉淀收获
```

### 沉淀大于测试

**测试是验证，沉淀是学习**：
- 测试是为了确认假设
- 沉淀是为了理解世界
- 理解世界比确认假设更重要

**沉淀清单**：
- [ ] 今天学到了什么？
- [ ] 有什么新发现？
- [ ] 有什么新灵感？
- [ ] 有什么新假设？
- [ ] 历史实验教会了什么？

**每次实验后的沉淀**：
```markdown
## 📚 今天沉淀

### 新学到
- <知识点1>
- <知识点2>

### 新发现
- <发现1>

### 新灵感
- <灵感1>

### 对历史的反思
- <反思1>
```

## ⚡ 快速参考（必背）

### 核心原则（永不暂停）
1. **研究是核心** — 查资料、反思、总结是主要任务
2. **每个地图同等重要** — 没有"总分"概念
3. **新 ARCH 从 Start-Kit 开始** — 不要从当前最优开始
4. **验证期不超过 3 次** — 信号明确后立即停止
5. **永不等人工** — 永远不要等待人工输入或审批
6. **永不暂停** — 永远在做事，要么研究、要么实验、要么分析
7. **本地分数是唯一决策依据** — 云端分数仅供参考，不影响本地决策
8. **鼓励复杂方向** — 优先尝试大改动，避免无意义调参
9. **沉淀大于测试** — 资料积累比分数更重要

### 信号判断（考虑方差）
| 类型 | 标准 | 行动 |
|------|------|------|
| **明确提升** | 低方差地图 +5% 或 高方差地图 +15%，且无下降 | **立即 commit** |
| **明确失败** | ≥2 个地图下降 >5% | **立即换方向** |
| **信号不明确** | 其他情况 | **反思后决定** |

### 避免重复测试

**重复测试是浪费**：
- 同一代码测 3 次 = 浪费 2 次
- 方差内重复测试 = 无法得出新结论
- 调参期间反复测试 = 不会学到新东西

**测试的真正目的**：
- 验证新假设（新方向、新架构）
- 确认方向有效/无效
- 不是"多测几次看分数" |

### 预算
- 每个方向：**最多 5 次实验**
- 每个 ARCH：**最多 30 次实验**

### 暂停条件（满足任一即暂停）
- 连续 3 次失败/无信号
- 连续 3 次成功
- 预算耗尽

### 回退原则
- 回退后**不测试**（看编译即可）
- 回退后**不开新方向**（记录原因即可）

### 评分等级
| 等级 | 标准 |
|------|------|
| 🥇 显著提升 | 多个低方差地图 +5% |
| 🥈 有提升 | 至少1个低方差地图 +5% |
| 🥉 边缘 | 提升 <5% |
| ⚠️ 风险 | 无提升或下降 |

## ⭐ 核心原则（必须牢记）

### 原则一：新架构以纯净基准为起点（2026-04-19 重大更新）

> **⚠️ 警告：绝对禁止 checkout 旧 commit 来"回到 Start-Kit"！**
>
> **"从 Start-Kit 纯净基准开始"的含义**：
> - **不要**：执行 `git checkout <old-commit>`
> - **不要**：执行 `git reset --hard <old-commit>`
> - **应该**：继续在当前代码上微调，或新建实验方向
>
> **原因**：checkout 旧 commit 会导致：
> 1. 编译失败（依赖缺失、API 不匹配）
> 2. 混淆 example 文件和轮次文件
> 3. 丢失已验证的改进（H1 等）
>
> **开新 ARCH 的正确方式**：
> - 在当前 HEAD commit 上继续微调
> - 或使用 `git stash` 暂存当前更改，然后开新方向
> - **绝对不要 checkout 到旧的 "Start-Kit" commit**
>
> **澄清**：这个原则只用于**开新 ARCH** 时。维护当前最优 baseline 时不适用（不要为了"纯净"而回退已验证的改进）。

### 原则二：每个地图分数同等重要

> **评估改进时，没有"总分"概念。每个地图分数同等重要，改进必须体现在至少一个地图上，且不能伤害其他地图。**

### 原则三：避免重复测试（新增，2026-04-19）

> **测试是为了验证假设，不是为了收集数据。** 同一个代码跑超过 3-4 次测试就是浪费。
>
> **触发重复测试警告的情况**：
> - 代码没变，跑超过 3 次测试
> - 回退代码后，马上跑测试"验证回退成功"（回退是否成功看编译对不对，不需要跑完整测试）
> - 同一个实验方向跑超过 5 次总测试
>
> **正确做法**：
> - 测试 1-2 次确认信号（提升/下降）→ 记录 → 继续下一个方向
> - 如果信号不明确，先研究原因，不要继续盲目测试
> - **验证回退：看编译，不跑完整测试**

### 原则四：记录必须包含 commit ID + exe MD5（2026-04-19 新增）

> **每条测试记录必须包含以下信息，否则记录无效：**
>
> | 字段 | 说明 | 示例 |
> |------|------|------|
> | **commit** | Git commit ID | `9b8e044` |
> | **exe MD5** | lifelong.exe MD5 | `A5BE4835A01A5937D92E5EB605656DC9` |
> | **Round** | 测试轮次 | `Round 362` |
> | **日期** | 测试日期 | `2026-04-19` |
> | **地图分数** | 每个地图的分数和tasks | fulfill: 0.788 (788) |
>
> **为什么重要**：
> - 没有 commit = 不知道分数对应哪个代码
> - 没有 MD5 = 不知道可执行文件是否正确
> - 记录混乱/乱码 = 记录无效
>
> **获取 MD5 命令**：`Get-FileHash build/lifelong.exe -Algorithm MD5`
>
> **检查清单（记录前必做）**：
> ```
> 记录前检查：
> □ commit ID 正确？
> □ exe MD5 正确？
> □ 分数没有乱码？
> □ 记录完整？
> ```

### 原则四：架构探索需要调试期和验证期（新增，2026-04-19）

> **架构探索分为两个阶段，需要不同的策略。**
>
> **调试期（让代码能跑）**：
> - 编译失败 → 继续调试
> - 0 分 / crash → 继续调试
> - 没有任何限制，直到代码能跑通
> - **这个阶段只追求让程序跑起来，不追求分数**
>
> **验证期（确认改进）**：
> - 代码跑通后，才进入验证期
> - 用 1-2 次测试确认信号（提升/下降）
> - **信号明确后立即记录，然后继续下一个方向**
> - **不要继续跑更多测试收集"更多数据"**
>
> **区分标准**：
> - 调试期：编译失败、程序崩溃、分数为 0 或异常低
> - 验证期：程序正常运行，分数在合理范围
>
> **调试期的耐心**：
> - 同一个编译错误试 10 次不算多
> - 同一个方向调试 20 次也不算多
> - **只要在进步（编译进步、分数进步），就继续**
>
> **验证期的纪律**：
> - 确认信号后**立即停止测试**
> - 继续下一个方向或休息
> - **验证期跑超过 3 次测试 = 浪费**
>
> **危险信号（需要停止并换方向）**：
> - 代码能跑了，但方向 A 跑了 5+ 次，分数一直在 baseline 附近波动
> - 多次实验方向都没有改善信号
> - 发现假设根本上是错误的
>
> **ARCH 饱和判定**：
> - 同一个 ARCH 10+ 次实验都没有显著提升 → 饱和
> - 饱和后开新 ARCH，**不要 checkout 旧 commit**，在当前 HEAD 继续微调

### ⚠️ 未完成工作禁止开新 ARCH（2026-04-19 重大更新）

> **🚨 绝对禁止：丢弃未完成的工作去开新 ARCH！**

**错误案例**：
- 创建了 LNS skeleton 但没集成 → 宣布"饱和" → 要开新 ARCH ❌
- 实验才 6 次 → 宣布"ARCH 探索完" → 要开新 ARCH ❌

**正确做法**：
```
未完成的活儿没干完 = 禁止开新 ARCH

开新 ARCH 之前必须检查：
□ 所有 H# 实验都完成了（成功/失败/证伪）？
□ 所有 skeleton 都集成了？
□ 所有待实验方向都试过了？
□ 真的没有新方向可以尝试了？

如果有任何"没干完" → 继续干完
只有真的干完了 → 才能开新 ARCH
```

**饱和的准确定义**：
| 情况 | 是否饱和 |
|------|---------|
| 6 个实验，未完成的 H3/H4 | ❌ 不是饱和，是没干完 |
| 10+ 实验，所有方向都失败 | ✅ 饱和 |
| 10+ 实验，有方向成功但已达上限 | ✅ 饱和 |
| 10+ 实验，但还有 skeleton 没集成 | ❌ 不是饱和，是丢弃工作 |

### 🔄 恢复程序

**代码损坏时**：
```bash
git log --oneline  # 查看最近的好提交
git checkout <good-commit> -- .  # 恢复到好的版本
```

**测试结果丢失时**：
- 测试结果在 `test-scripts/round/roundXXX/` 目录
- 如果目录损坏，只能重新测试
- 记录到项目笔记，下次更加小心

**记录文件损坏时**：
- src/MAPF-records.md 有 git 历史，可以恢复
- 项目笔记.md 建议定期备份到外部

### 📍 状态真实来源（Single Source of Truth）

| 状态 | 真实来源 | 备份 |
|------|---------|------|
| 当前代码 | `git log -1` 的 commit | git history |
| 当前分数 | `roundXXX/scores.txt` | src/MAPF-records.md |
| 假设状态 | src/MAPF-records.md | git history |
| 知识库 | src/MAPF-records.md | git history |
| 待实验队列 | src/MAPF-records.md | git history |

**原则**：
- 不要在多个地方重复存储同一状态
- 以 git commit 为代码的真实来源
- 以 src/MAPF-records.md 为实验记录的真实来源

## 核心原则

1. **不研究，不动手** — 代码改变之前，必须有充分的研究支撑
2. **不放弃，无记录** — 每一个被跳过的方向必须记录"放弃原因"和"替代方案"
3. **不浅尝辄止** — 一个方向必须完成"最小完整验证"（4轮+）才能换方向
4. **用固定脚本** — 所有操作使用 `test-scripts/build.bat`、`run_quick_test.bat` 等固定脚本
5. **优先改算法** — 修改 `src/my_planner/` 下的算法实现，而不是堆在4个接口文件里
6. **不建 branch** — 所有工作在 main branch，ARCH 标记仅在 commit message 中
7. **大胆尝试** — 可以重写整个架构；可以用低分做新 ARCH 基线；不要因为短期分低就否定架构改动
8. **重视方差** — 快速测试单轮方差可达 ±5%，必须通过多次测试或完整测试确认信号

### 目录结构
```

│
├── MAPFPlanner.cpp          ← 调用 MyPlanner
├── Executor.cpp             ← 调用 MyPlanner
└── TaskScheduler.cpp        ← 自定义调度器（ARCH-Z）

default_planner/             ← 保持原样，不允许修改
```

1. `src/MAPFPlanner.cpp` → 调用 `MyPlanner::plan()`

- 信号明确后**立即记录，然后继续下一个方向**
- **不要跑超过 3 次！**

### 信号判断标准（考虑方差）

**高方差地图**（fulfill, random）：变化 >10% 才算明确
**低方差地图**（bos, room, maze, orz, iron）：变化 >5% 算明确

**明确提升**：
- ≥1 个低方差地图提升 >5%，或
- ≥1 个高方差地图提升 >15%，且无地图下降 >5%

**明确失败**：
- ≥2 个地图下降 >5%

**信号不明确**：其他情况 → 反思

**注意**：高方差下，1-2 次测试不能确定结论。如果第一次显示提升但不确定，等待下次触发时再验证。

### 流程

```
1. 研究完成 → 提案记录到 src/MAPF-records.md
2. ✅ 完成改前检查清单
3. 运行 build.bat
4. 如果编译失败 → 调试期 → 修复 → 返回步骤3
5. 运行 run_quick_test.bat
6. 检查结果：
   a. 如果是调试期（第一次跑通）→ 记录"跑通" → 进入验证期
   b. 如果是验证期（第1-2次）→ 评估信号
7. 信号判断：
   - 明确提升 → commit → 继续下一个方向
   - 明确失败/信号不明确 → 进入反思
8. 反思后决定：调整假设 / 换方向 / 暂停休息

### Git 回退策略

**何时需要回退**：
- 云端反馈显示分数大幅下降（>10%）
- 本地验证发现引入 bug
- 连续多次实验都失败

```bash

git revert <commit>  # 创建新提交反转改动

**回退后处理**：

3. 更新知识库（记录"此路不通"）
4. 进入反思阶段

**不要做的事**：
- 回退后"再测试一次验证回退成功"（看编译即可）
- 在回退代码上继续开发（应该开新方向）

### 错误处理

**编译错误**：
```
1. 查看错误信息
2. 如果是规则错误（改了禁止文件）→ 立即回退
3. 如果是逻辑错误 → 修复 → 继续调试
4. 记录错误类型到项目笔记
```

**运行时错误（Crash）**：
```
1. 查看错误日志
2. 如果是确定性问题 → 修复 → 继续调试
3. 如果是随机性问题 → 重试 1-2 次
4. 记录错误类型
```

**测试结果异常**：
```

2. 如果某个地图分数远低于 baseline → 可能有问题
3. 如果所有地图都远低于 baseline → 立即回退
```

## 阶段 9：反思（而非简单放弃/继续）

**当验证期结果不明确或失败时**，不是简单地"继续"或"放弃"，而是停下来反思：

```markdown
### 🤔 ARCH-X Ry — <方向> — 反思

**验证结果**：
- 测试1：random=X, bos=X, ..., fulfill=X
- 测试2：random=X, bos=X, ..., fulfill=X
- 信号判断：明确提升 / 明确失败 / 信号不明确

**反思问题**：
1. **假设验证**：原假设成立吗？证据是什么？
2. **失败原因**：是假设错了？还是实现有bug？还是参数问题？
3. **新发现**：这次尝试中发现了什么新信息？
4. **调整策略**：基于新信息，下一步应该：
   - 调整假设继续
   - 换方向
   - 换 ARCH

**决定后的行动（永不等待）**：
- 调整假设继续 → 记录新假设 → 立即进入下一个实验
- 换方向 → 记录到待实验队列 → 立即继续下一个方向
- 换 ARCH → 从 Start-Kit 重新开始（新 ARCH）→ 立即开始
```

**永不暂停机制**：
- 方向失败 → 立即换方向（不暂停）
- 方向成功 → 立即继续或提交云端（不等待）
- 预算耗尽 → 立即开新ARCH（不犹豫）
- 云端等待中 → 本地继续研究其他方向（不等云端）

**永远有事做**：
- 如果没有待实验方向 → 研究新方向
- 如果研究完成 → 提案+执行
- 如果所有方向都失败 → 开新ARCH重新开始
- 如果云端等待中 → 研究其他方向
```

### 定时触发机制（Heartbeat）

**触发频率**：
- 永远活跃：每次触发都要做事

**检查清单**（每次触发 - 永远有事做）：
```
1. 是否有待实验方向？
   └─ 有 → 立即执行
   └─ 无 → 立即研究新方向

2. 当前方向是否失败/饱和？
   └─ 是 → 立即换方向/开新ARCH
   └─ 否 → 继续当前方向

3. 有什么可以改进的地方？
   └─ 有 → 立即执行
   └─ 无 → 研究冠军代码寻找新灵感

4. 有云端反馈？
   └─ 有 → 记录到 src/MAPF-records.md（不等待，不影响决策）
   └─ 无 → 继续

**核心**：永远不要说"没有事做"，永远基于本地分数决策
```

**状态标记**：
```markdown
## 永远活跃状态

|------|------|------|
| 🟢 执行中 | 执行实验/研究 | 继续执行 |
| 🟡 研究中 | 研究新方向 | 继续研究 |
| 🔄 分析中 | 分析云端反馈 | 继续分析 |

**永远不会有「暂停」「等待」「休眠」状态**
```

### 消融实验 (Ablation Study)

**什么时候需要消融实验**：
- 当一个改动包含多个子改动时
- 当你不确定哪个子改动起作用时
- 当需要理解每个组件的贡献时

**消融实验的设计**：
```markdown
## 🧪 消融实验: A1-R1 (多改动分析)

**原始改动**: 改动A + 改动B + 改动C

**基线**: Start-Kit 或 当前最佳

**实验设计**：
| 实验 | 改动 | fulfill | bos | ... | 总分 |
|------|------|---------|-----|-----|------|
| 基线 | 无 | 0.50 | 0.20 | ... | 基础 |
| 实验1 | A | 0.52 | 0.21 | ... | +X |
| 实验2 | A+B | 0.55 | 0.22 | ... | +Y |
| 实验3 | A+B+C | 0.58 | 0.24 | ... | +Z |

**分析**：
- C 的贡献 = (实验3 - 实验2)
- B 的贡献 = (实验2 - 实验1)
- A 的贡献 = (实验1 - 基线)
```

**消融实验的原则**：
- 每次只改变一个组件
- 保持其他所有条件不变
- 记录所有结果，不要只记录"好的"

### 因果分析 (Causal Analysis)

**为什么需要因果分析**：
- 相关性 ≠ 因果性
- 看到提升后，需要理解**为什么**提升了
- 避免把运气当作能力

**因果分析的步骤**：
```
1. 观察：看到现象（fulfill 提升 10%）
2. 假设：提出可能的因果机制
3. 验证：设计实验验证因果机制
4. 结论：这个改动确实导致了提升
```

**因果分析模板**：
```markdown
## 🔬 因果分析: <改动>

**观察到的现象**：
<具体描述>

**可能的因果假设**：
H1: <假设1>
H2: <假设2>

**验证方法**：
- H1: <如何验证>
- H2: <如何验证>

**结论**：
- <哪个假设被验证/否定>
- <对实践的影响>
```

**常见因果错误**：
| 错误 | 错误原因 | 正确做法 |
|------|---------|---------|
| 相关性当因果 | 时间上的巧合 | 控制变量 |
| 混淆变量 | 有其他变量影响 | 消融实验 |
| 确认偏误 | 只看支持证据 | 记录负面结果 |

### 方向选择原则

**优先复杂方向，慎用调参**：

| 类型 | 描述 | 优先级 | 示例 |
|------|------|--------|------|
| 🔴 复杂方向 | 架构改动、算法替换 | **最高** | LNS、Dist2PathHeuristicTable |
| 🟡 中等方向 | 调度算法改进、新算法引入 | 高 | Hungarian调度、区域划分 |
| 🟢 小改动 | 参数调整、已有算法微调 | 低 | 贪心阈值、惩罚系数 |

**为什么优先复杂方向**：
- 调参容易遇到天花板（已饱和）
- 复杂方向可能带来突破性提升
- 调参的成功往往已经被之前的实验覆盖

**调参的陷阱**：
- 反复调参 5+ 次还不提升 → 说明方向错了，不是参数问题
- 参数微调提升 <2% → 可能是方差，不是真正的提升
- 调参成功往往是找到了前人已知的最佳参数

**决策规则**：
```
调参 3 次无提升 → 立即换方向（不是继续调）
调参提升 <2% → 需要 3+ 次验证确认（可能是方差）
复杂方向优先 → 即使失败也能学到东西
```

**实验优先级矩阵**

| 方向类型 | 假设强度 | 实现难度 | 潜在收益 | 优先级 |
|----------|---------|---------|---------|--------|
| 复杂架构 | 高 | 高 | 高 | **P0** |
| 算法替换 | 高 | 中 | 高 | **P0** |
| 调度改进 | 中 | 低 | 中 | P1 |
| 参数微调 | 低 | 低 | 低 | P2 |

**假设强度评估**：
- 3分：冠军代码验证过的做法
- 2分：有论文/理论支持
- 1分：直觉/猜测

**实现难度评估**：
- 3分：需要较大架构改动
- 2分：需要中等改动
- 1分：只需参数调整

**潜在收益评估**：
- 3分：可能带来 >10% 提升
- 2分：可能带来 5-10% 提升
- 1分：可能带来 <5% 提升

**优先做能改变架构的方向，而不是反复调参**

### 资源消耗追踪

**为什么要追踪资源**：
- 时间是有限的
- 需要知道每个方向的投入产出比
- 避免在一个方向上投入过多

**资源追踪表**：
```markdown
## ⏱️ 资源消耗

| 方向 | 研究时间 | 实验次数 | 总耗时 | 产出 |
|------|---------|---------|--------|------|
| priority管理 | 2h | 2 | 4h | +7% fulfill |
| causalPIBT改动 | 1h | 2 | 2h | -25% fulfill |
| TaskScheduler调参 | 0.5h | 1 | 1h | 无显著变化 |
```

**效率评估**：
- 高效率：投入 <2h，产出 >5%
- 中效率：投入 2-5h，产出 1-5%
- 低效率：投入 >5h，产出 <1%

**资源决策**：
- 低效率方向 → 及时止损，换方向
- 高效率方向 → 可以继续深挖
```

### 统计分析原则

**最小样本量**：
- 低方差地图：1-2 次测试
- 高方差地图：3-5 次测试

**显著性判断**：
- 低方差地图：变化 >5% 即显著
- 高方差地图：变化 >15% 才显著

**置信度**：
- 本地测试：80% 置信度（筛选）
- 云端测试：95% 置信度（确认）

### 盲测原则

**为什么要盲测**：
- 避免确认偏误：期望看到好结果时会忽视坏信号
- 减少过度优化：不想"捡芝麻"而丢失大局

**盲测做法**：
1. **分析前先假设**：先写下预期，再看结果
2. **记录所有结果**：不要只记录"好的"结果
3. **独立评估**：让结果自己说话，不要"脑补"
4. **同行评审**：让 HEARTBEAT.md 的状态成为"同行"，客观评价

### 可复现性

**可复现性的要求**：
- 相同代码 + 相同测试 = 相同结果（统计意义上）
- 不同机器、不同时间 = 可能不同（方差）

**提高可复现性**：
- 使用固定的 random seed（如果支持）
- 记录测试环境
- 记录测试时间

**可复现性检查**：
- 同一代码跑两次，结果是否在方差范围内？
- 如果结果差异超过方差范围 → 可能有 bug

### 趋势判断标准

| 趋势 | 判断 | 行动 |
|------|------|------|
| 连续 5 轮上升 | 好方向 | 继续 |
| 连续 5 轮下降 | 可能饱和 | 反思 |
| 波动但无明显趋势 | 正常 | 继续 |
| 突然大幅下降 | 可能有问题 | 检查/回退 |

### 高方差地图处理

| 地图 | 方差级别 | 单次测试价值 |
|------|---------|--------------|
| fulfill | 高 (±10-20%) | 低 |
| random | 高 (±5-10%) | 低 |
| bos | 低 (±2-3%) | 高 |
| room | 低 (±2-3%) | 高 |
| maze | 低 (±2-3%) | 高 |
| orz | 低 (±2-3%) | 高 |
| iron | 低 (±2-3%) | 高 |

**处理策略**：
- **优先相信低方差地图的结果**
- 高方差地图需要 3+ 次测试才能确认趋势
- 如果低方差地图都提升，但 fulfill 下降 → 整体判断为"提升"
- 如果 fulfill 大幅提升但其他都下降 → 需要进一步验证

## ❌ 常见错误

### 代码相关

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 修改了禁止文件 | 实验无效，可能丢分 | 改前检查清单 |
| 在回退代码上继续开发 | 浪费预算，丢分 | 开新方向或新 ARCH |
| 不 commit 就测试 | 状态不一致 | 先 commit 再测试 |

### 测试相关

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 验证期跑超过 3 次 | 浪费时间和资源 | 信号明确后立即停止 |
| 回退后"再测试验证" | 浪费测试预算 | 看编译即可 |
| 单次测试后下结论 | 被方差误导 | 多次测试确认 |

### 记录相关

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 不记录失败 | 重复犯错 | 失败后更新知识库 |
| 不更新假设追踪 | 假设状态混乱 | 每次实验后更新 |
| 忘记更新 Round | 状态不一致 | 测试后立即更新 |

### 研究相关

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 不读冠军代码就动手 | 重复造轮子 | 必须读完再实验 |
| 研究超过 2 小时 | 效率低 | 超时强制产出 |
| 没有假设就写代码 | 方向不明确 | 先有假设再动手 |

## ❓ FAQ（常见问题）

**Q: 方向失败了怎么办？**
A: 记录到知识库（已验证无效），更新假设追踪为 ❌，换方向。

**Q: ARCH 饱和了怎么办？**
A: 开新 ARCH，从 Start-Kit 重新开始。记录饱和报告。

**Q: 云端和本地结果矛盾怎么办？**
A: 以云端为准。本地可能是方差误解。回退代码，重新审视假设。

**Q: 连续多次失败怎么办？**
A: 暂停，反思。可能是方向错了，需要换方向。

**Q: 没有方向可以尝试了怎么办？**
A: 重新研究冠军代码，寻找新灵感。也可以研究论文。

**Q: 如何判断是方差还是真实提升？**
A: 看低方差地图。高方差地图需要多次测试。

**Q: 可以同时做多个方向吗？**
A: 不可以。一次只改一个方向，一次只验证一个假设。

**Q: 回退后代码丢失了怎么办？**
A: 用 `git log` 找到回退前的 commit，用 `git checkout` 恢复。

**Q: 测试结果在哪里？**
A: `test-scripts/round/roundXXX/scores.txt`。每个 round 一个目录。

**Q: 如何知道当前是哪个 ARCH？**
A: 查看 `git log --oneline` 的最新 commit message，里面有 ARCH 标记。
